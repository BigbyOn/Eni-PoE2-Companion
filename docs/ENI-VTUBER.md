# Eni-VTuber bridge

Локальный JSON-мост, через который Eni-VTuber получает данные Eni-PoE2 и
пользуется его торговой логикой. Мост не дублирует игровой парсер, оверлей и
билды: он вызывает те же модули, что и приложение.

## Сборка

```powershell
cd E:\Eni-PoE2-Companion
cargo build --bin eni-poe2-bridge          # быстрая debug-сборка
cargo build --release --bin eni-poe2-bridge
```

Готовый файл: `target\<профиль>\eni-poe2-bridge.exe`.

VTuber ищет его по порядку:

1. `eni.poe2.bridge_path` в `conf.yaml`;
2. переменная `ENI_POE2_BRIDGE`;
3. соседняя папка `Eni-PoE2-Companion/target/{release,debug}/eni-poe2-bridge.exe`.

Если путь задан явно и файла нет — мост не подменяется другим бинарником:
ошибка честно уходит в ответ.

## Протокол

Один JSON-объект на stdin → один JSON-объект на stdout (JSON-lines), либо
`--request '<json>'` для одного вызова. `--data-dir <path>` переопределяет
`ENI_COMPANION_DATA_DIR`.

Запрос:

```json
{"id":"1","method":"state","params":{}}
```

Ответ:

```json
{"id":"1","ok":true,"result":{...}}
{"id":"2","ok":false,"error":{"code":"no_build","message":"..."}}
```

Коды ошибок: `unknown_method`, `no_profile`, `no_build`, `bad_params`,
`no_item_text`, `item_not_parsed`, `no_league`, `no_filters`, `bad_guide_query`,
`bad_items`, `bridge_missing`, `bridge_timeout`.

## Методы

| Метод | Что делает |
|---|---|
| `meta` | версия, каталог данных, лига, билды, гайды, число решений |
| `state` | зона, акт, уровень, билд, этап, ближайшая цель, чего не хватает |
| `decisions.add` | сохранить ситуацию, совет, решение и причину |
| `decisions.list` | список решений (фильтры `build_id`, `patch`, `stage_id`) |
| `decisions.delete` | удалить запись по `id` |
| `decisions.similar` | похожие подтверждённые решения для того же билда и патча |
| `item.evaluate` | разобрать предмет и оценить под билд; сравнение только с явно переданным `equipped_text` или `equipped_by_slot` того же слота |
| `trade.price` | цена по явной команде через официальный trade API |
| `trade.search` | фильтры + ссылка на поиск, при `auto:true` — до трёх лотов |
| `trade.plan` | запрос на каждый слот, точная категория и проверка типа лота, не больше одного лота на слот, проверка бюджета |
| `upgrade.plan` | слоты и приоритеты из билда; без надетых предметов — `basis: build_priority` |
| `slots.suggest` | подсказки модов для слотов из гайда/этапа |
| `budget.plan` | проверить комплект на общий и поштучный лимит |
| `rates` | курс лиги с источником и свежестью |

`state` никогда не выдумывает данные: `stale` и `zone_basis` считаются по
последнему **игровому** событию из истории, а не по дате `state.json`. Если
активность клиента не подтверждена, возвращается `zone_basis: "last_known"` и
«последняя известная зона»; изменение настроек или профиля не делает зону живой.
`state` также отдаёт `character.id` (стабильный ID профиля) и `league`.

## Память решений

Файл: `<data_dir>/decisions.json`, запись атомарная (tmp + rename), не более
500 записей.

```json
{
  "schema": 1,
  "records": [{
    "id": "d-...",
    "created": "2026-11-15T16:20:00Z",
    "build_id": "lightning-arrow-deadeye",
    "build_name": "Lightning Arrow — Deadeye",
    "stage_id": "lvl-15-27",
    "stage_title": "15–27 уровень",
    "patch": "0.5.5",
    "situation": "Не хватает маны на боссе",
    "advice": "Взять узел на ману",
    "decision": "Взял узел на скорость",
    "reason": "Быстрее чищу паки, маны хватает с флаконом",
    "tags": [],
    "source": "voice"
  }]
}
```

Правила:

* запись без ситуации, решения или причины отклоняется;
* `decisions.similar` рассматривает **только** записи с тем же `build_id` и тем
  же `patch`; пустой билд или патч не совпадает ни с чем;
* запасной список по этапу (когда похожих нет) тоже фильтруется по `build_id` и
  `patch`; ручной просмотр истории может не указывать патч.
* похожесть ищется по ситуации, решению и причине (с разными весами), поэтому
  обычный вопрос «Стоит менять лук?» находит поправку про лук; порог 0.12,
  совпадение этапа добавляет 0.1 к рангу, но не расширяет область поиска;
* это поиск по памяти, а не дообучение модели.

Безопасность записи: мост пишет **только** `decisions.json`. `state.json` он
только читает, поэтому не конфликтует с запущенным приложением.

## Бюджет и курсы

`budget.plan` принимает позиции с ценой, валютой и лигой, общий лимит и лимит на
предмет. Правила жёсткие:

* сумма всех принятых позиций не может превышать общий лимит;
* каждая позиция проверяется по поштучному лимиту;
* позиции из другой лиги отклоняются, а не смешиваются;
* пересчёт идёт по курсу **той же лиги** из `scout.json` (poe2scout, 24 ч);
  `rates.source` и `rates.age_seconds` возвращаются в ответе; курс старше 6 ч
  считается устаревшим;
* смешанные валюты с отсутствующим/устаревшим курсом не подтверждают бюджет:
  `budget_known: false`, `fits: false`;
* повтор слота отклоняется: альтернативные лоты одного слота не складываются в
  комплект;
* если комплект не проходит, `accepted` содержит только частичный вариант в
  порядке приоритета, а `violations` объясняют причину.

Обязательный тест: два предмета по 15 ex при общем лимите 20 ex не могут быть
приняты одним комплектом (`fits: false`, принято меньше двух).
Он есть и в Rust (`budget::tests`), и в интеграционных тестах VTuber.

## Поиск апгрейдов

`trade.plan` (голос и панель используют один и тот же ответ):

* принимает несколько слотов за раз; для каждого строит свой запрос и проверяет,
  что каждый явный фильтр попал в итоговый `query.stats` (`filters_applied`), а
  не попавший — в `filters_unmatched` (тогда нельзя говорить, что он применён);
* использует точные категории (`armour.boots`, `accessory.belt`, ...); для
  оружия категория широкая, ссылка подписана, а лоты без подтверждённого типа в
  комплект не включаются;
* полученный лот повторно сверяется по `baseType`/`typeLine`: кольцо на запрос
  пояса пропускается (`skipped_types`);
* явные моды добавляются к готовому запросу гайда, заменяя значение того же
  стата, а не дублируя его;
* ценовой предел — меньшее из поштучного и общего лимита, в валюте расчёта; если
  хотя бы один из двух лимитов не переводится курсом, предел не подставляется и
  оба ограничения не подтверждаются;
* при `auto: false` лоты не запрашиваются: на каждый слот возвращается ссылка и
  фраза «Лоты не получены, итоговую стоимость комплекта проверить не могу»;
* при `auto: true` берётся не больше одного лота на позицию, и только эти
  котировки уходят в `budget::plan`; альтернативы одного слота не суммируются;
* `totals.candidates_total` — сумма всех кандидатов, `totals.accepted_total` —
  только принятых. Если в бюджет проходит часть, сумма кандидатов не называется
  стоимостью рекомендованного комплекта;
* лига резолвится строго: явно запрошенная недоступная лига — ошибка
  `league_unavailable` со списком доступных, без тихого перехода;
* `upgrade.plan` берёт слоты и приоритеты из активного билда/гайда и помечает
  результат `basis: build_priority`, если надетые предметы не переданы.

`trade.search` остаётся одиночным инструментом для MCP; `item.evaluate` сравнивает
только с явно переданным `equipped_text` того же слота и никогда — с последним
импортированным предметом.

## Общий код с приложением

Мост компилирует те же файлы, что и Tauri-приложение: `model`, `builds`,
`campaign`, `guide`, `item`, `trade`, `trade_i18n`, `scout`, `pob`, плюс новые
`decisions`, `budget`, `companion`.

Конвертация валют вынесена в `budget::convert`; приложение использует её в
`to_divine` для списка апгрейдов, мост — в бюджете. Одна реализация на оба
потребителя.

## Проверка

```powershell
cargo test decisions            # память решений
cargo test budget               # жёсткий бюджет и курсы
cargo test companion            # состояние, предметы, поиск, бюджет
cargo test                      # весь набор
```

Ручная проверка моста:

```powershell
echo '{"id":"1","method":"meta"}' | .\target\debug\eni-poe2-bridge.exe
```

## Ограничения

* надетую экипировку приложение не знает (её не отдаёт ни журнал, ни API),
  поэтому вердикт предмета — «подходит под билд», а не «апгрейд»;
* сеть используется только в `trade.price` и `trade.search` с `auto: true`;
* автономного управления персонажем нет и не будет: мост ничего не отправляет
  в игру.
